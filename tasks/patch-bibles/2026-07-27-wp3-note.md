#### The canonical policy I chose, and why

One type, `Core/Agent/RouteTargetPolicy.swift`, holding **one rule with two tunings**.
The rule:

1. **Peak** each provider to its tightest (highest-used) window — that reading *is* the
   provider.
2. **Then gate on trust**: confidence ∈ `routableConfidences` and not older than
   `maxRoutableAge` (30 min).
3. **Route to the least-filled trusted peak**, only when ≥`minTrustedProviders` (2)
   providers have one, it is below `avoidThreshold` (85), and it clears the tuning's
   `minSpread` / `maxRouteTargetPercent` bars.
4. **Avoid** every peak at/over `avoidThreshold`, trusted or not.

`.agent` = `minSpread: 0`, `maxRouteTargetPercent: nil` (the issue's flat 85% rule).
`.ui` = `minSpread: 15`, `maxRouteTargetPercent: 70` — identical trust gate.

Why this shape rather than one of the three existing answers:

- The agent rule was already the *correct* one (it is the one `f725bac` hardened and the
  one `AgentRecommendationEngineTests` encodes), so it became the base. The two UI
  heuristics were the ones with the bug, not the ones with the better rule.
- The ≥15-point spread and the 70% ceiling are **presentation** decisions, not routing
  decisions — "don't nag a human over a 2-point difference" is meaningless advice to an
  agent, which wants the best available answer even in a tight field. So they stayed
  *parameters* of the shared rule and are asserted in tests to apply to `.ui` only
  (`testSpreadGateAppliesToUITuningOnly`, `testRouteTargetCeilingAppliesToUITuningOnly`).
  They never silently became the agent rule.
- **Peak-then-gate ordering preserved and re-commented** on the new type: a provider whose
  tightest window is untrusted must not become routable via a looser confirmed one. Now
  covered by a test at the policy level *and* at the chip level.
- **avoid-from-all / routeTo-from-trusted asymmetry preserved**: `avoid` reads every peak,
  `routeTo` only trusted peaks. Both halves are asserted in
  `RouteTargetPolicyTests.testAvoidIncludesUntrustedReadingsButRoutingDoesNot` on top of
  the existing engine tests.
- `MaxxerMath.swift` did **not** move (project.yml is out of scope and shared with WP-1/WP-4).
  It keeps its path and its test-bundle compilation; `routeTarget` is now a 1-line delegation.

#### Risks / watch-outs

- **Behaviour change on two view surfaces, on purpose.** `DashboardView` and `OverviewView`
  previously had *no* threshold; they now require a trusted reading, a ≥15-point spread and
  a ≤70% target. The route chip / headroom dot will appear **less often** than before. That
  is the fix, but it is a visible change and worth one look during manual QA.
- **The ≥2-provider bar is now counted in providers, not readings.** `MaxxerMath.routeTarget`
  used to count raw `utilizations`, so two windows from one provider satisfied it. Now each
  provider is peaked first. More correct ("routing implies a choice" between providers), and
  no existing test depended on the old counting.
- **The named account tracks `ClaudeCodeProvider.headlineQuotaWindows` by convention, not by
  construction.** If WP-2 or a later change alters how the provider picks its headline
  account, `AgentRecommendationEngine.headlineAccount` must change with it or it will name
  the wrong account. Documented in a doc comment at both ends; nothing enforces it.
- **A real defect I found live but did NOT fix (out of my scope — `Core/Providers/`):**
  `headlineQuotaWindows` picks the account with the lowest peak **regardless of
  confidence**. On this machine right now the `default` account serves a `local_estimate`
  5% while `account-1` (official 11%) and `account-2` (official 6%) both have real
  readings — so the untrusted account wins the headline and the trust gate then excludes
  the *whole provider* from routing. Two good accounts are masked by one stale one. See
  the live output below. Worth its own package; it is the same "a stale number is not
  evidence" principle, applied one layer lower.
